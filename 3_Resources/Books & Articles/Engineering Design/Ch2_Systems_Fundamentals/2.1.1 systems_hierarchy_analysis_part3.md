# 🧠 PART 6: MNEMONIC DEVICES

## Memory Aids for Systems Thinking

### Mnemonic 1: BODIES Framework (System Boundary Definition)

**B**oundary - Where do you draw the line?
**O**utputs - What leaves the system?
**D**ecomposition - How to subdivide?
**I**nputs - What enters the system?
**E**nvironment - What's outside?
**S**ubsystems - Internal divisions

**Vietnamese**: **BỐ DIES** (Bố = Father, guiding your system definition)

**Usage**: When starting any new design, mentally checklist BODIES

**C**onstruction - How is it BUILT?
**P**roduction - How to MAKE it?

**M**aintenance - How to SUSTAIN it?

## Applying Mnemonics in Practice

**Example: Defining Naval Gun Mount System**

**Step 1**: BODIES framework
- **B**oundary: From base ring to gun barrel (excluding ammunition)
- **O**utputs: Aimed gun barrel (position), fired rounds (kinetic energy), status signals
- **D**ecomposition: Will use FCP-AM (multiple viewpoints)
- **I**nputs: Electrical power (440V, 60Hz), fire commands, ammunition (manual loading)
- **E**nvironment: Ship deck (vibration, salt spray), operators, target vessels
- **S**ubsystems: Traverse drive, elevation drive, gun barrel, recoil system, fire control

**Step 2**: FCP-AM viewpoints
- **F**unctional: Aim gun, Fire round, Absorb recoil, Protect crew
- **C**onstruction: Barrel assembly, Mount base, Drive motors, Recoil cylinder
- **P**roduction: Import barrel (foreign), Manufacture base (local), Assemble drives
- **A**ssembly: Mount base → Install drives → Attach barrel → Test fire
- **M**aintenance: Level 1 (lubricate), Level 2 (replace motors), Level 3 (barrel refurbishment)

**Step 3**: EMS flows
- **E**nergy: 440V AC in → Mechanical rotation + translation out
- **M**aterial: Ammunition in → Fired rounds out, Lubricant in → Waste oil out
- **S**ignal: Fire commands in → Gun position out, Status data out

**Step 4**: Interface spec (TYPES-CR) for barrel-to-mount
- **T**ype: Mechanical (structural)
- **Y**ou: Barrel supplier designs, you design mounting points
- **P**arameters: 50kN recoil force, ±30° elevation, ±180° traverse
- **E**nvironment: Salt spray, vibration 3G peak, -20°C to +50°C
- **S**tandard: MIL-STD-810 (environmental), STANAG 4418 (ammunition compatibility)
- **C**riticality: HIGH (mission-critical, single point of failure)
- **R**esponsibility: Supplier verifies barrel strength, you verify mount strength

**Result**: Complete system definition in <20 minutes using mnemonics

## Stock-Flow Model of Design Process

**Key Stocks** (What Accumulates):

1. **Design Knowledge** (Information stock)
   - Current level: Beginner/Intermediate/Advanced
   - Inflows: Study sessions, practice, feedback from reviews
   - Outflows: Forgetting (decay over time)

2. **Decomposition Artifacts** (Work products)
   - Current level: Number of completed decompositions
   - Inflows: Design work, documentation
   - Outflows: Obsolescence (requirements change)

3. **Interface Documentation** (Critical buffer)
   - Current level: % of interfaces fully specified
   - Inflows: Interface definition work
   - Outflows: Interface changes (design iteration)

4. **Team Understanding** (Shared mental model)
   - Current level: Alignment on system boundaries
   - Inflows: Communication, reviews, teaching
   - Outflows: Turnover (people leave), confusion (ambiguity)

**Key Flows** (Rates of Change):

- **Learning rate**: Hours/week studying systems thinking
- **Application rate**: Systems decomposed/month
- **Error rate**: Mistakes in boundary definition
- **Correction rate**: Errors caught and fixed
- **Documentation rate**: Interfaces specified/day

### Fatigue Management Rules

**1. Never exceed 2 hours continuous study**
```
If study session > 2 hours:
├─ Decision quality degrades
├─ Error rate increases
└─ False sense of progress (re-reading ≠ learning)
```

**2. Use Pomodoro breaks strategically**
```
During 5-min breaks:
✅ DO: Walk, stretch, hydrate, bathroom
✅ DO: Close eyes, deep breathing
❌ DON'T: Check email, social media (drains focus)
❌ DON'T: Start conversations (context-switching cost)
```

**3. Match task difficulty to energy level**
```
High energy (morning):
- Learn new concepts
- Solve hard problems
- Deep analysis

Medium energy (afternoon):
- Practice familiar skills
- Apply to examples
- Review and consolidate

Low energy (evening):
- Light practice
- Journaling

```

- Re-reading same paragraph 3+ times

# 📋 PART 11: SELF-ASSESSMENT RUBRICS

## Rubric 1: System Boundary Definition Quality

| Criterion | Level 1 (Poor) | Level 2 (Basic) | Level 3 (Good) | Level 4 (Excellent) |
|-----------|----------------|-----------------|----------------|---------------------|
| **Clarity** | Vague, ambiguous | Boundary stated but unclear where line is | Clear line drawn, most components classified | Crystal clear, no ambiguity, anyone could understand |
| **Completeness** | Missing inputs or outputs | Main I/O identified, some missing | All I/O identified | All I/O identified AND documented with specs |
| **Rationale** | No explanation for choices | Brief mention of why | Clear reasoning provided | Explicit decision rationale + trade-offs discussed |
| **Stakeholder Alignment** | Boundary conflicts with others | Some disagreement remains | General agreement | Documented agreement from all parties |
| **Documentation** | Not written down | Verbal description only | Written but informal | Formal doc: diagram + specifications + signatures |

**How to use**: Rate yourself on each criterion. If any "Level 1" scores → needs improvement before proceeding.

---

## Rubric 2: Functional Decomposition Quality

| Criterion | Level 1 | Level 2 | Level 3 | Level 4 |
|-----------|---------|---------|---------|---------|
| **Solution Neutrality** | Functions describe specific technologies | Functions mostly neutral, some technology bias | Functions fully neutral (what, not how) | Neutral + alternative physical principles identified for each |
| **Completeness** | Major functions missing | Most functions present, some gaps | All required functions | All required + validated against requirements |
| **Hierarchy Depth** | Too shallow OR too deep | Reasonable but inconsistent | Consistent depth, appropriate detail | Optimal depth justified, consistent |
| **Flow Definition** | Flows not identified | Flows mentioned vaguely | Energy/Material/Signal identified | Flows fully specified with quantities |
| **Testability** | Can't verify function achieved | Partially testable | All functions testable | Test criteria defined for each function |

---

## Rubric 3: Interface Specification Quality

| Criterion | Level 1 | Level 2 | Level 3 | Level 4 |
|-----------|---------|---------|---------|---------|
| **Type Definition** | Interface type unclear | Type stated (e.g., "electrical") | Type + direction specified | Full characterization (type, direction, standard) |
| **Parameters** | No numerical values | Vague values ("high voltage") | Specific values (28V DC) | Values + tolerances + ranges (28V ±2V, 5-15A) |
| **Criticality** | Not assessed | Mentioned informally | Rated (High/Med/Low) | Rated + failure mode analysis |
| **Responsibility** | Ownership unclear | "Someone should..." | Named person/team | Matrix: Who designs, verifies, owns changes |
| **Change Control** | No process | Ad-hoc changes | Documented process | Formal process + version control |

**Use this when**: Reviewing your design before presenting to team or mentor.

# 🎯 PART 12: TARGETED DRILL MASTER

## Common Weak Areas & Targeted Practice

### Weakness 1: Boundary Definition Too Large/Small

**Diagnostic**: You consistently define boundaries that:
- Include components you don't control (too large)
- Miss critical interactions (too small)

**Drill Set 1: Boundary Sizing Practice (15 min)**

For each system, define boundary, then check against answer:

**Problem 1**: UAV autopilot
- What's inside: [Your answer]
- Check: Should include sensors, processor, control algorithms. Should EXCLUDE motors (those are actuators in separate subsystem), airframe (separate), power supply (environment).

**Problem 2**: Coastal radar power supply
- What's inside: [Your answer]
- Check: Should include AC-DC converter, voltage regulators, filters. Should EXCLUDE generator (environment), radar electronics (separate), cables to subsystems (interfaces only).

**Problem 3**: Naval gun recoil system
- What's inside: [Your answer]
- Check: Should include recoil cylinder, recuperator, mount structure. Should EXCLUDE barrel (separate), ammunition (environment), fire control (separate).

**Repetition schedule**: Daily for 1 week, then weekly until error rate <10%.

---

### Weakness 2: Mixing Functional and Construction Decomposition

**Diagnostic**: Your decomposition mixes "what it does" with "how it's built"

**Example of mixing**:
```
❌ BAD:
Radar System
├─ Antenna (construction)
├─ Detect targets (function)
├─ Transmitter box (construction)
└─ Track targets (function)
```

**Drill Set 2: Pure Decomposition Practice (20 min)**

**Problem**: Artillery fire control system

**Step 1**: Create ONLY functional decomposition
- Don't mention any physical components
- Use only action verbs (detect, compute, control, display)

**Step 2**: Create ONLY construction decomposition
- Don't mention any functions
- Use only physical nouns (antenna, processor, console, cable)

**Step 3**: Create mapping table
```
Function → Implemented by Construction
F1: Detect target → Radar assembly
F2: Compute trajectory → Ballistic computer
[etc.]
```

**Repetition**: 3x per week for 2 weeks on different systems.

---

### Weakness 3: Vague Interface Specifications

**Diagnostic**: You write interfaces like "connects to power" instead of "28V DC ±2V, 5-15A, MIL-STD-704"

**Drill Set 3: Interface Specification Completeness (15 min/day)**

Take this incomplete interface and make it complete:

**Before**: "Radar connects to display unit via cable"

**Your improved version**:
```
Interface Name: ___________
Type: ___________
Direction: ___________
Specification: ___________
Standard: ___________
Criticality: ___________
```

**Check against answer**:
```
Interface Name: Radar-to-Display Data Link
Type: Digital data (RS-485 serial)
Direction: Bidirectional (radar sends tracks, display sends commands)
Specification: 115200 baud, 8-N-1, differential signaling, <100m cable length
Standard: TIA/EIA-485, MIL-STD-1553 electrical characteristics
Criticality: MEDIUM (display failure doesn't prevent radar operation)
```

**Practice on**: 5 interfaces/day for 2 weeks.

---

### Weakness 4: Decomposition Too Deep

**Diagnostic**: You decompose down to individual screws and washers

**Drill Set 4: Optimal Depth Practice (20 min)**

**Rule**: Stop decomposing when you reach one of these:
1. Subsystems can be assigned to separate teams
2. Subsystems can be purchased as COTS items
3. Further detail doesn't help current design phase
4. You've reached 4 levels (typical max)

**Problem**: Decompose a man-portable radar

**Your decomposition**: [Create levels]

**Check**: Should stop at:
```
Level 1: Radar System
Level 2: Antenna Assembly, Electronics Assembly, Display Assembly, Power Assembly
Level 3: (For Electronics) RF Frontend, Signal Processor, Interface Board
Level 4: (For Signal Processor) ADC Card, FPGA Card, CPU Card

STOP HERE. Don't decompose to resistors and capacitors on FPGA Card.
```

**Practice**: 10 different systems, find optimal depth for each.

# 🎯 PART 14: RECOMMENDED USE CASES

## When to Apply This Knowledge

### Use Case 1: Starting New Defense Project

**Trigger**: You receive requirements for new military system development

**Application**:
1. **Week 1**: Define system boundary using BODIES framework
2. **Week 2**: Functional decomposition (understand WHAT system must do)
3. **Week 3**: Initial construction decomposition (HOW might it be built)
4. **Week 4**: Production decomposition (make/buy decisions, technology transfer planning)
5. **Ongoing**: Interface specification (document ALL interfaces before subsystem teams start work)

**Success Metric**: Design review passes with minimal comments on system definition

---

### Use Case 2: Reverse Engineering Foreign System

**Trigger**: Acquired foreign military equipment, need to understand for local production

**Application**:
1. **Construction decomposition**: Disassemble physical hardware, document structure
2. **Functional decomposition**: Test to understand WHAT it does (without knowing HOW)
3. **Production decomposition**: Identify components that could be made locally vs. must import
4. **Maintenance decomposition**: Define field-replaceable units for local military

**Success Metric**: Can produce local variant with 50%+ indigenous content

---

### Use Case 3: Technology Transfer Negotiation

**Trigger**: Negotiating with foreign supplier on what they provide vs. what you develop

**Application**:
1. **System boundary**: Define clearly what supplier provides (black box) vs. what you control
2. **Interface specification**: Rigorously document ALL interfaces supplier must meet
3. **Production decomposition**: Identify subsystems for license manufacture vs. import

**Success Metric**: No interface surprises during integration, clear contractual boundaries

---

### Use Case 4: Design Review Preparation

**Trigger**: Presenting your design to senior engineers, managers, or customer

**Application**:
1. **Choose decomposition viewpoint** based on audience:
   - Technical review → Functional + Construction decomposition
   - Management review → Production decomposition (costs, schedule)
   - Customer review → Functional decomposition (requirements satisfaction)
2. **Document interfaces** thoroughly
3. **Prepare rationale** for system boundary decisions

**Success Metric**: Reviewers understand design quickly, approve to proceed

---

### Use Case 5: Troubleshooting Integration Failures

**Trigger**: Subsystems work individually but fail when integrated

**Root Cause**: Unclear interfaces, boundary mismatches

**Application**:
1. **Re-examine system boundaries**: Did teams interpret boundaries differently?
2. **Check interface specs**: Were ALL interfaces fully specified?
3. **Map functional to construction**: Does physical structure implement all required functions?

**Success Metric**: Identify root cause, implement fix, prevent future similar issues

---

### Use Case 6: Training Junior Engineers

**Trigger**: Onboarding new team members to project

**Application**:
1. **Show system decomposition**: Here's the big picture
2. **Assign subsystem**: Here's YOUR boundary, YOUR interfaces
3. **Provide templates**: Use these docs for interface specs, decomposition
4. **Review regularly**: Check their understanding of how their subsystem fits whole

**Success Metric**: Junior engineers work independently with minimal rework

---

### Use Case 7: Proposal Development

**Trigger**: Bidding on new defense contract

**Application**:
1. **System boundary**: Define scope of what you're proposing
2. **Production decomposition**: Identify team partners (who does what)
3. **Cost breakdown**: Map to subsystems from decomposition
4. **Risk analysis**: Identify critical interfaces, single points of failure

**Success Metric**: Win contract, then deliver as proposed (no scope creep)

---

## Critical Success Factors

For ALL use cases:

**DO**:
- ✅ Define system boundary FIRST, document rationale
- ✅ Choose decomposition viewpoint consciously (functional, construction, production, maintenance)
- ✅ Specify interfaces rigorously BEFORE subsystem work begins
- ✅ Use templates and checklists
- ✅ Review with stakeholders for alignment

**DON'T**:
- ❌ Skip system boundary definition ("we all know what we're building")
- ❌ Mix decomposition viewpoints unconsciously
- ❌ Assume interfaces will "work out" during integration
- ❌ Decompose too deep too early
- ❌ Work in isolation without stakeholder feedback

## Industry-Specific Adaptations

### For Vietnamese Defense Industry:

**Special Considerations**:
1. **Technology transfer constraints**: Many subsystems will be black boxes from foreign suppliers
   - Solution: Define interfaces extra carefully, accept functional specs without construction details
2. **Supply chain interruptions**: Import dependencies create risk
   - Solution: Production decomposition should identify 2-3 alternative suppliers per critical component
3. **Limited design catalogs**: Can't just pick components from Western catalogs
   - Solution: Build internal library of proven components from past projects
4. **Security classifications**: Some subsystems classified differently
   - Solution: Decomposition must align with security boundaries (unclass, confidential, secret)
5. **Maintenance philosophy**: Often component-level repair vs. Western LRU swap
   - Solution: Maintenance decomposition must go deeper (to component level, not just assemblies)
