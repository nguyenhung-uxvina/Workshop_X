# 📚 FRAMEWORK 1: FEYNMAN TECHNIQUE - Simple Explanation

## 🎓 60-Second Explanation (Giải Thích 60 Giây)

**What is Task Clarification?**

Task Clarification is the critical first phase where you answer THREE fundamental questions before designing anything:
1. **What must this solution DO?** (Objectives - Mục tiêu)
2. **What properties MUST it have?** (Demands - Yêu cầu bắt buộc)
3. **What properties must it NOT have?** (Constraints - Ràng buộc)

The result is a **Requirements List** (Danh sách yêu cầu) - your design's "birth certificate" that defines success.

## 🏠 Everyday Analogy

**Building a House (Xây Nhà)**

Before any architect draws a single line, they ask:
- **Objectives**: "What is this house for?" (Family with 2 kids? Elderly couple? Work-from-home professional?)
- **Must Have**: "4 bedrooms, 2 bathrooms, wheelchair accessible, faces south"
- **Must NOT Have**: "No stairs on main floor, no windows facing noisy road"

The Requirements List is like the architectural brief - without it, the architect might design a beautiful house that nobody can live in.

## 🎯 Defense Application Example: Target USV

**The Task**: Design an unmanned surface vessel for naval gunnery training

**Before Task Clarification (Wrong Approach)**:
"Let's just build a fast boat with remote control!"
→ Result: $50K boat that doesn't simulate real radar signature, sinks after first hit, can't be recovered

**After Task Clarification (Right Approach)**:

| Question | Answer for Target USV |
|----------|----------------------|
| **What must it DO?** | Simulate enemy patrol boat for weapons training |
| **Must HAVE** | RCS ≥ 5m², speed ≥ 35 knots, remote control range ≥ 20km, survivability against 12.7mm rounds |
| **Must NOT HAVE** | Cannot sink in 1 hit, no hazardous materials after destruction |

## 💡 Why This Matters

**Without Task Clarification**:
- 73% of project failures trace to requirements problems (source: INCOSE studies)
- Design changes cost 10-100× more in later phases
- "Scope creep" destroys budgets and schedules

**With Task Clarification**:
- Clear success criteria for design reviews
- Prevents "moving goalposts"
- Enables parallel work (different teams can work on verified requirements)

## Chunk 1: What is Task Clarification? (30 min)
**Difficulty**: ⭐
**Prerequisites**: None

### Core Concepts (5 items)
1. Task Clarification = Phase 1 of systematic design
2. Purpose: Define success criteria BEFORE designing
3. Output: Requirements List (specification document)
4. Prevents: Requirements drift, scope creep, design rework
5. Foundation for all subsequent phases

### Key Distinction
- **Task Description** (input): "Design a target boat for training"
- **Requirements List** (output): Detailed specification with 50+ quantified items

### Defense Example
**Training Grenade Task Description**: "Design an inert grenade for infantry training"

This is NOT enough! Task Clarification transforms this into:
- Weight: 430g ± 10g (matches real M67)
- Fuse delay: 4.5 ± 0.5 seconds
- Sound output: ≥ 120 dB at 3m
- Smoke generation: Visible for 10+ seconds
- Cost per unit: ≤ $15

## Chunk 2: Sources of Design Tasks (45 min)
**Difficulty**: ⭐⭐
**Prerequisites**: Chunk 1

### Core Concepts (6 items)
1. **Development Order**: From product planning or external customer
2. **Definite Order**: Specific customer contract with specifications
3. **Internal Request**: From sales, research, test, or assembly staff
4. **Market Analysis**: Identified opportunity without specific customer
5. **Problem Report**: Field failures or deficiencies
6. **Regulatory Change**: New standards require redesign

### Three Task Elements
Every task contains:
1. **Product statements**: Functionality, performance
2. **Deadline statements**: Development, production, delivery dates
3. **Cost targets**: Development budget, unit cost, lifecycle cost

## Chunk 3: The Three Fundamental Questions (60 min)
**Difficulty**: ⭐⭐
**Prerequisites**: Chunks 1-2

### Core Concepts (5 items)
1. **Objectives**: What must the solution SATISFY?
2. **Positive Properties**: What must it HAVE?
3. **Negative Properties**: What must it NOT HAVE?
4. All three questions must be answered in cooperation with client/proposer
5. Answers must be quantified wherever possible

### Question Deep-Dive

#### Question 1: What objectives must the solution satisfy?
- Mission-level goals
- Operational context
- User needs (not wants)

**UAV Catapult Example**:
- Launch 150kg UAV to 25 m/s within 5m track length
- Enable launch in crosswind up to 15 m/s
- Support 20 launches/day without component replacement

#### Question 2: What properties must it HAVE?
- Functional requirements (what it does)
- Performance requirements (how well)
- Interface requirements (how it connects)
- Environmental requirements (where it operates)

**Radar-IR Target Simulation Example**:
| Category | Must Have |
|----------|-----------|
| Functional | Generate 10 m² radar cross-section |
| Performance | Signature stable ± 10% across 8-12 GHz |
| Interface | Compatible with standard NATO IFF interrogators |
| Environmental | Operate in -20°C to +50°C ambient |

#### Question 3: What properties must it NOT have?
- Safety exclusions (what could cause harm)
- Regulatory exclusions (what's prohibited)
- Operational exclusions (what would prevent use)

**Training Grenade Example**:
| Must NOT Have | Reason |
|---------------|--------|
| Fragmentation | Safety - training environment |
| Toxic smoke | Safety - respiratory protection |
| Weight > 500g | Realism - must match real grenade |
| Visible "TRAINING" marking < 5mm | Realism - shouldn't be obvious from 2m |

## Chunk 4: Requirements List Structure (60 min)
**Difficulty**: ⭐⭐⭐
**Prerequisites**: Chunks 1-3

### Core Concepts (7 items)
1. **Demands (D)**: Must be met - non-negotiable
2. **Wishes (W)**: Desirable - can be traded off
3. **Quantitative**: Numbers, ranges, limits (preferred)
4. **Qualitative**: Descriptions when numbers impossible
5. **Source tracking**: Who requested each requirement
6. **Change control**: Formal process for modifications
7. **Living document**: Updated throughout project

### Requirements List Layout (Figure 5.2)

```
┌─────────────────────────────────────────────────────────────┐
│ REQUIREMENTS LIST                      Issued: [Date]       │
│ for: [Product Name]                    Page: [N] of [M]     │
├─────────┬───┬────────────────────────────────────┬──────────┤
│ Changes │D/W│ Requirements                       │Responsible│
├─────────┼───┼────────────────────────────────────┼──────────┤
│ [Date]  │ D │ [Category]: [Quantified requirement]│ [Name]   │
│         │ W │ [Objective with qualitative data]   │          │
├─────────┴───┴────────────────────────────────────┴──────────┤
│ Split by: □ Subsystems  □ Functions  □ Checklist headings   │
└─────────────────────────────────────────────────────────────┘
```

### Standard Checklist Categories (Figure 5.3)

1. **Geometry**: Size, height, width, diameter, weight
2. **Kinematics**: Motion type, velocity, acceleration
3. **Forces**: Load direction, magnitude, frequency
4. **Energy**: Power input/output, efficiency, losses
5. **Material**: Properties, standards, environmental impact
6. **Signals**: Input/output, display, control
7. **Safety**: Protection, fail-safe, hazards
8. **Ergonomics**: Human factors, interface
9. **Production**: Factory limitations, tolerances
10. **Quality control**: Inspection, testing standards
11. **Assembly**: Installation, commissioning
12. **Transport**: Size limits, weight limits, protection
13. **Operation**: Environment, modes, procedures
14. **Maintenance**: Service intervals, access, training
15. **Costs**: Development, unit, operation, disposal
16. **Schedules**: Milestones, delivery dates

| D | Geometry | Mass: 25kg ± 2kg | Towing aircraft limit |

## Chunk 5: QFD Introduction (45 min)
**Difficulty**: ⭐⭐⭐
**Prerequisites**: Chunks 1-4

### Core Concepts (5 items)
1. **QFD**: Quality Function Deployment (Triển khai chức năng chất lượng)
2. **Purpose**: Translate customer wishes → product requirements
3. **House of Quality**: Matrix relating customer needs to technical specs
4. **Voice of Customer**: Raw user desires before engineering translation
5. **Supports but doesn't replace**: Requirements list still needed

### When to Use QFD

| Situation | Use QFD? | Reason |
|-----------|----------|--------|
| Major long-term project | ✅ Yes | Extensive effort justified |
| Small adaptation design | ❌ No | Simpler methods in Chapter 5 sufficient |
| Customer requirements unclear | ✅ Yes | Structured translation needed |
| Military specification exists | ⚠️ Maybe | QFD reveals gaps in spec |

### QFD Benefits for Defense Projects

1. **Better requirements formulation** through customer representation
2. **Critical function identification** (customer-oriented)
3. **Technical requirements prioritization** based on customer impact
4. **Future development goals** identification
5. **Competitor analysis** integration

### Defense Example: QFD for Target USV

**Voice of Customer** (Navy Training Command):
- "We need realistic targets that don't sink immediately"
- "Should be recoverable and reusable"
- "Must look like a real boat on radar"

**QFD Translation**:

| Customer Need | Technical Requirement | Target Value |
|---------------|----------------------|--------------|
| Realistic target | Radar cross-section | 5-10 m² |
| Doesn't sink | Hull material strength | Withstand 7.62mm |
| Recoverable | Self-bailing capability | Drain 100 L/min |
| Reusable | Modular damage panels | Replace in < 2 hours |

### Common Deficiencies in Defense Task Clarification

| Deficiency | Symptom | Corrective Action |
|------------|---------|-------------------|
| Hidden solutions | "Requirements" specify technology choices | Rewrite in terms of function/performance |
| Untestable requirements | "Shall be reliable" without metrics | Add MTBF, failure rate numbers |
| Missing constraints | Cost overruns, schedule slip | Review budget, schedule requirements |
| Single stakeholder focus | User needs met, maintainer ignored | Stakeholder analysis, all roles |
| Copy-paste from similar project | Requirements don't match new context | Fresh three-question analysis |

## Mnemonic 3: D vs W Classification

### 🎯 Target Concept
Distinguishing Demands (must have) from Wishes (nice to have)

### 🧠 Primary Mnemonic
**Type**: Visual + Rule
**Mnemonic**: **"D = Death if missing, W = Would be nice"**

Vietnamese: **"D = Điều kiện sống còn, W = Ước muốn thêm"**

### 📖 Component Breakdown
- **D (Demand)**: If this requirement is not met, the product CANNOT fulfill its purpose
- **W (Wish)**: If this requirement is not met, the product is still usable but less desirable

### 💡 Memory Reinforcement
**Test Question**: "If this requirement is missing, is the product DEAD (unusable)?"
- YES → Mark as **D**
- NO → Mark as **W**

**Defense Example**:
- Training Grenade weight = 430g (D) - Too heavy → trainees learn wrong technique → training value DEAD
- Training Grenade color = OD Green (W) - Different color → still works → training value alive

### ✅ Quick Recall Test
1. A Target USV requirement says "Speed ≥ 35 knots" - D or W? Why?
2. A UAV Catapult requirement says "Painted camouflage color" - D or W? Why?

# 📚 FRAMEWORK 9: SYSTEMS MAPPER - Feedback Loops in Task Clarification

## System Map: Task Clarification Process

### Key Stocks

| Stock | Type | Unit | Description |
|-------|------|------|-------------|
| Requirements Completeness | Information | % complete | How much of requirements space is covered |
| Stakeholder Alignment | Information | Conflict score | Agreement level among stakeholders |
| Requirements Quality | Information | Score 0-4 | Clarity, testability, consistency |
| Project Risk | Capability | $ exposure | Risk due to requirements uncertainty |

### Key Flows

| Flow | Direction | Rate | Description |
|------|-----------|------|-------------|
| Requirements Discovery | Inflow | Items/week | New requirements identified |
| Requirements Validation | Outflow | Items/week | Requirements verified with stakeholders |
| Scope Creep | Inflow | Items/week | Uncontrolled requirement additions |
| Quality Improvement | Inflow | Score/review | Improvements from reviews |

### Feedback Loops

#### R1: Knowledge-Discovery Loop (Reinforcing)

```
[Design Knowledge] +→ [Requirements Discovery Rate] +→ 
[Requirements Completeness] +→ [Conceptual Design Progress] +→ 
[Design Knowledge] [CLOSES]
```

**Effect**: More design work → more requirements discovered → better specifications → better design work
**Implication**: Early design exploration improves requirements quality

#### B1: Review-Correction Loop (Balancing)

```
[Requirements Quality Gap] +→ [Review Intensity] +→ 
[Issues Found] +→ [Corrections Made] -→ 
[Requirements Quality Gap] [CLOSES]
```

**Effect**: Poor quality triggers reviews → reviews find issues → corrections improve quality → gap closes
**Implication**: Regular reviews are essential; skipping reviews lets quality degrade

#### R2: Scope Creep Spiral (Reinforcing - DANGEROUS)

```
[Scope Creep] +→ [Requirements List Size] +→ 
[Complexity] +→ [Confusion] +→ 
[Unclear Boundaries] +→ [Scope Creep] [CLOSES]
```

**Effect**: Uncontrolled additions → bigger list → more complex → less clear boundaries → more additions
**Implication**: Must establish change control EARLY to break this loop

### Leverage Points for Task Clarification Success

| Level | Intervention | Impact |
|-------|--------------|--------|
| L3 (Goals) | Define "complete" before starting | Very High |
| L5 (Rules) | Establish change control process | High |
| L6 (Information) | Real-time stakeholder alignment dashboard | High |
| L9 (Delays) | Short review cycles (weekly, not monthly) | Medium |
| L12 (Parameters) | Checklist category count | Low |

# 📚 FRAMEWORK 11: SELF-ASSESSMENT RUBRIC GENERATOR

## Self-Assessment Rubric: Task Clarification Deliverables

### Rubric 1: Requirements List Quality

**Use after**: Creating requirements list for any system

| Criterion | Unsatisfactory (1) | Developing (2) | Proficient (3) | Exemplary (4) |
|-----------|-------------------|----------------|----------------|---------------|
| **Three Questions** | Missing 2+ questions | 1 question incomplete | All 3 answered but not deep | All 3 thoroughly answered with examples |
| **Quantification** | < 30% quantified | 30-50% quantified | 50-70% quantified | > 70% quantified with appropriate precision |
| **D/W Classification** | Not classified or arbitrary | Classification present but inconsistent | Consistent with minor errors | Clear reasoning for each classification |
| **Checklist Coverage** | < 8 categories | 8-12 categories | 12-15 categories | All 16 categories with appropriate depth |
| **Source Tracing** | No sources documented | Some sources noted | Most sources documented | Full traceability with stakeholder sign-off |
| **Defense Integration** | No defense standards | Generic standards reference | Specific MIL-STD/STANAG cited | Standards mapped to requirements with verification |

**Scoring Guide**:
- 20-24: Ready for design review
- 15-19: Minor revisions needed
- 10-14: Major revisions required
- 6-9: Restart with mentor guidance

### Rubric 2: Stakeholder Analysis Quality

| Criterion | Unsatisfactory (1) | Developing (2) | Proficient (3) | Exemplary (4) |
|-----------|-------------------|----------------|----------------|---------------|
| **Identification** | Only 1-2 stakeholders | 3-4 stakeholders | 5-7 stakeholders | 8+ with rationale for inclusion |
| **Interest Analysis** | Interests not documented | Vague interests stated | Specific interests per stakeholder | Interests quantified/prioritized |
| **Conflict Recognition** | No conflicts identified | Some conflicts noted | Conflicts documented with parties | Conflict resolution plan included |
| **Communication Plan** | No plan | Ad-hoc communication | Regular updates planned | Stakeholder-specific communication strategy |

### Self-Assessment Process

1. **Complete the work** (requirements list or stakeholder analysis)
2. **Wait 24 hours** (fresh perspective)
3. **Score each criterion honestly** (1-4)
4. **Calculate total score**
5. **Identify lowest 2 criteria** (improvement focus)
6. **Create action plan** (specific fixes)
7. **Revise and re-score** (verify improvement)
