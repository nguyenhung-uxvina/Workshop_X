## Executive Summary

Section 6.3.3 provides **11 practical guidelines** for establishing function structures during conceptual design. This analysis applies all 13 Meta-Learning skills from the EDMF to extract maximum learning value and enable systematic application to Vietnamese defense/security training systems.

**Core Insight:** Function structures are tools for discovering solutions—not ends in themselves. The degree of detail depends on task novelty and designer experience.

**Key Distinction:**
- **Original Design:** Start from requirements list → abstract problem → build function structure
- **Adaptive Design:** Analyze existing solution → extract function structure → vary to find improvements

## 1. Feynman Technique Explanation

**Skill:** `engineering-feynman`

### 60-Second Explanation

Imagine you're writing a recipe book for cooking machines. Section 6.3.3 teaches you HOW to write those recipes (function structures) in practice. It gives you 11 specific tips:
1. Start simple and break down complex steps gradually
2. Focus on the main cooking process first before worrying about cleanup
3. Remember that every step matters equally—even "turn off the stove" is as important as "add ingredients"

### Everyday Analogy: Planning a Wedding

Function structures are like breaking down "host a wedding" into sub-tasks:
- **Main flow:** Ceremony → Reception → Departure
- **Auxiliary flows:** Catering, Photography, Music

**Guideline 11 says:** "Photos" and "flowers" are equally important—without either, the wedding isn't complete.

**Guideline 7 says:** You can vary the structure:
- Combine ceremony + reception (integrated function carrier)
- Change the order (reception before ceremony?)
- Move the boundary (include rehearsal dinner or not?)

### Defense Application Example: 12.7mm Remote Controlled Weapon Station (RCWS)

| Design Type | Approach |
|:------------|:---------|
| **Original Design** | Requirements list → Overall function "engage targets remotely" → Decompose into: Detect Target → Track Target → Aim Weapon → Fire Weapon → Provide Feedback |
| **Adaptive Design** | Analyze existing RCWS → Extract function structure → Vary by adding "Stabilize Platform" or changing from manual to automatic tracking |
| **Signal Flow (Figure 6.11)** | Detect (camera/radar) → Process (fire control computer) → Activate (servo motors) → Indicate (operator display) → Operate (manual override) |

### Common Misconception

❌ **Wrong:** "Auxiliary functions like cooling or safety interlocks are less important than the main firing function."

✅ **Correct:** All functions are equally important. A RCWS that can fire but overheats is useless. Eliminate only truly unnecessary functions—not "seemingly unimportant" ones.

### Quick Understanding Check

**Question:** For a Target USV (Unmanned Surface Vehicle), which function is "most important"?
- A) Propulsion
- B) Navigation  
- C) Target signature presentation
- D) All are equally important

**Answer:** D. Per Guideline 11, technical systems don't have functions that are "more important" or "less important." All functions are needed; any function not needed should be eliminated.

### Chunk 1: Starting Approach (Guidelines 1-2)

**Theme:** Begin rough, refine systematically

**G1 - Progressive Refinement:**
- First derive a ROUGH function structure with few subfunctions
- Break down step-by-step by resolving complex subfunctions
- Can substitute a first solution idea, then abstract to derive other subfunctions
- Can work from system boundary inwards (identify boundary-crossing functions first)

**G2 - Handling Unclear Relationships:**
- If no clear relationships exist, enumerate subfunctions without logical/physical connections
- Arrange by extent of realization (which are most developed?)
- This allows search for first solution principle

**Defense Example - Training Grenade:**
```
Rough Structure (G1):
┌─────────────────────────────────────────┐
│ Training Grenade Overall Function       │
│ "Simulate grenade effects safely"       │
└─────────────────────────────────────────┘
         ↓ Decompose
┌──────────┐  ┌──────────┐  ┌──────────┐
│ Accept   │→ │ Delay    │→ │ Generate │
│ Arming   │  │ Effect   │  │ Signature│
└──────────┘  └──────────┘  └──────────┘
```

**Practice Exercise:**
Create a rough function structure (3-5 subfunctions) for a LOMAH (Location of Miss and Hit) system. Don't overthink—start rough!

### Chunk 2: Flow Management (Guidelines 3-4)

**Theme:** Logic and E-M-S completeness

**G3 - Logical Relationships:**
- Logical relationships lead to function structures where working principles (mechanical, electrical, hydraulic) can be anticipated
- Shows which domains solutions might come from

**G4 - E-M-S Flow Completeness:**
- Function structures are NOT complete until Energy, Material, and Signal flows are specified
- **Strategy:** Start with MAIN FLOW (determines design, easier to derive)
- Add auxiliary flows for: fault handling, power transmission, control
- Complete structure obtained by ITERATION

**Defense Example - Target UAV Signal Flow:**
```
Main Flow (Energy/Material):
[Fuel] → Convert → [Thrust] → Transmit → [Motion] → Convert → [Lift]

Auxiliary Flow (Signals):
[Flight Command] → Process → [Motor Commands] → Transmit → [Actuators]
[Sensor Data] → Process → [Telemetry] → Transmit → [Ground Station]
```

**Key Insight:** Don't try to specify all flows at once. Iterate: main flow first, then auxiliary flows, then integration.

---

### Chunk 3: Building Blocks (Guidelines 5-6)

**Theme:** Use standard functions as templates

**G5 - Generally Valid Functions (PGM):**
- Several subfunctions recur in most structures
- Use Figure 2.7 functions as starting points:
  - Convert, Transmit, Store, Connect, Channel, Change, Vary (Energy)
  - Convert, Transmit, Store, Connect, Channel, Change, Vary (Material)
  - Convert, Transmit, Store, Connect, Channel, Change, Vary (Signal)

**G6 - Signal Flow Functions for Microelectronics (Figure 6.11):**
```
┌─────────┐        ┌─────────┐        ┌──────────┐
│ Detect  │───────▶│ Process │───────▶│ Activate │
│(Sensors)│        │(Control)│        │(Actuators)│
└─────────┘        └────┬────┘        └──────────┘
     ▲                  │                   │
     │                  ▼                   │
     │            ┌─────────┐               │
     │            │Indicate │               │
     │            │(Display)│               │
     │            └─────────┘               │
     │                  │                   │
     └──────────────────┴───────────────────┘
                    ┌─────────┐
                    │ Operate │
                    │ (User)  │
                    └─────────┘
```

**Defense Example - AR-VR Weapon Simulator:**

| Signal Function | Implementation |
|:----------------|:---------------|
| **Detect** | Weapon position sensors, trigger sensors, user input devices |
| **Process** | Simulation computer, ballistics calculator, scenario engine |
| **Activate** | Haptic feedback motors, recoil simulation, visual rendering |
| **Indicate** | VR headset display, audio feedback, score display |
| **Operate** | User controls, instructor interface, scenario selection |

### Chunk 4: Variation Methods (Guideline 7)

**Theme:** Creating alternatives systematically

**G7 - Four Variation Methods (Mnemonic: CARS):**

| Method | Description | Example: Towed Target System |
|:-------|:------------|:-----------------------------|
| **C**ombine/Break | Break down or combine subfunctions | Combine "Deploy" and "Control" into single "Deploy-Control" module |
| **A**rrange | Change arrangement of subfunctions | Move "Generate IR Signature" before "Generate Radar Signature" |
| **R**econnect | Change switching (series/parallel/bridge) | Parallel IR and Radar signature generation instead of series |
| **S**hift Boundary | Move system boundary | Include winch system inside system boundary vs. as external |

**Why Variation Matters:**
Varying the function structure introduces DISTINCT solutions. Setting up function structures constitutes a FIRST STEP in the search for solutions.

**Practice Exercise - Radar-IR Target Simulation:**
Apply all 4 CARS methods to this rough function structure:
```
[Receive Command] → [Generate Radar Signature] → [Generate IR Signature] → [Transmit Data]
```

Create at least 3 variants using different methods.

### Chunk 5: Quality Control (Guidelines 8-11)

**Theme:** Simplicity, selection, and analysis

**G8 - Simplicity Principle:**
- Keep function structures SIMPLE to encourage simple, economical solutions
- Aim for INTEGRATED FUNCTION CARRIERS (one component fulfilling multiple functions)
- **Exception:** Use discrete functions for: clarity requirements, extreme loading, high quality demands

**G9 - Early Selection:**
- Only PROMISING function structures should proceed
- Apply selection procedure (Section 3.3.1) even at this early stage
- Don't waste resources developing all variants equally

**G10 - Simple Representation:**
- Use simple, informative symbols (Figure 2.4)
- Add task-specific verbal clarifications
- Avoid overly complex notation

**G11 - Analysis for Solution Search:**
- Analyze to identify:
  - Subfunctions needing NEW working principles
  - Subfunctions where KNOWN solutions exist
- Focus search effort on solution-determining subfunctions
- All other functions still necessary—just handled with less novel effort

**Critical Warning (End of Section):**
> "It is sometimes assumed wrongly that auxiliary functions are unimportant. Technical systems do not have functions that are 'more important' or 'less important'. All functions are important because they are needed."

## 3. Design Review Criteria

**Skill:** `engineering-design-review-mentor`

Use these criteria to evaluate function structure quality:

| Review Criterion | Pass Indicator ✓ | Fail Indicator ✗ |
|:-----------------|:-----------------|:-----------------|
| **Progressive Refinement** | Started rough (3-5 subfunctions), systematically decomposed | Jumped to detailed 20+ function structure immediately |
| **E-M-S Flow Completeness** | All three flow types present; main flow clear, auxiliary flows documented | Only energy flow shown; signals and materials missing |
| **PGM Usage** | Uses generally valid functions as building blocks (convert, transmit, store) | All subfunctions are task-specific without abstraction |
| **Signal Flow Pattern** | Uses Detect-Process-Activate-Indicate-Operate for control systems | Ad-hoc signal flow without standard pattern |
| **Variation Explored** | 2-3 variants using CARS methods documented | Single function structure with no alternatives |
| **Simplicity Principle** | Seeks integrated function carriers; simple and economical | Unnecessarily complex; every function has separate carrier |
| **Selection Applied** | Only promising structures proceed; clear selection rationale | All variants proceed without evaluation |
| **Representation Quality** | Simple symbols + verbal clarifications | Overly complex notation or no explanations |
| **New vs Known Analysis** | Clearly identifies which subfunctions need new vs known solutions | No distinction between novel and standard subfunctions |

### Defense System Review Checklist

**For any function structure (LOMAH, RCWS, Simulator, etc.):**

- [ ] Does the structure trace back to requirements list items?
- [ ] Is the main flow clearly identified and documented first?
- [ ] Are all three flow types (E-M-S) present where applicable?
- [ ] For control systems: Does it follow Detect-Process-Activate-Indicate-Operate pattern?
- [ ] Have at least 2 variants been generated using CARS methods?
- [ ] Is simplicity prioritized (integrated function carriers where appropriate)?
- [ ] Has early selection been applied with documented rationale?
- [ ] Are solution-determining subfunctions identified for focused search?

### Drill Set 2: CARS Variation Methods (G7)

**Problem 3 (Difficulty: ⭐⭐⭐⭐):**
Given this function structure for a Tethered Drone:

```
[Power Supply] → [Transmit Power] → [Convert to Thrust] → [Stabilize] → [Position Hold]
                                                              ↓
                                              [Transmit Video] → [Display]
```

Apply all 4 CARS methods to create 4 variants.

**Model Answers:**

**Variant 1 - Combine:**
```
[Power Supply] → [Transmit Power] → [Convert+Stabilize] → [Position Hold+Display]
```
Combined "Convert to Thrust" with "Stabilize" (both involve motor control)
Combined "Position Hold" with "Display" (both are user-facing outputs)

**Variant 2 - Arrange:**
```
[Power Supply] → [Transmit Power] → [Stabilize] → [Convert to Thrust] → [Position Hold]
                                        ↓
                        [Transmit Video] → [Display]
```
Moved "Stabilize" before "Convert to Thrust" (stabilize power before conversion)

**Variant 3 - Reconnect (Parallel):**
```
                         ┌→ [Convert to Thrust] → [Position Hold]
[Power Supply] → [Transmit Power] →│
                         └→ [Stabilize] ─────────────┘
                                  ↓
                         [Transmit Video] → [Display]
```
Parallel processing of thrust conversion and stabilization

**Variant 4 - Shift Boundary:**
```
System Boundary Expanded to Include Ground Station:

[External Power] → [Ground Processing] → [Transmit Power] → [Convert] → [Stabilize] → [Hold]
                           ↓                                    ↓
                    [Receive Video] ← ────────────────── [Capture Video]
```
System boundary now includes ground station processing

## 15. Summary and Key Takeaways

### The 11 Guidelines in One Page

| # | Guideline | Mnemonic | Key Action |
|:-:|:----------|:---------|:-----------|
| 1 | Start rough, decompose step-by-step | **R**ough | Begin with 3-5 subfunctions |

### Critical Reminders

> **"Function structures are intended to facilitate the discovery of solutions: they are not ends in themselves."**

> **"Technical systems do not have functions that are 'more important' or 'less important'. All functions are important because they are needed."**

> **"Varying the function structure introduces distinct solutions. The setting up of function structures constitutes a first step in the search for solutions."**

### Vietnamese Defense Context Adaptations

1. **Supply Chain:** Consider local manufacturing capabilities when deciding integration vs discrete (G8)
2. **Standards:** TCVN compliance may affect system boundary decisions (G7-Shift)
3. **Maintenance:** Three-level maintenance philosophy influences function decomposition depth
4. **Environment:** MIL-STD-810 tropical conditions affect auxiliary function requirements (cooling, sealing)
5. **Cost:** Indigenous production emphasis favors simpler structures (G8)

## Appendix A: Figure 6.11 Analysis

### Basic Signal Flow Functions for Modular Use in Microelectronics

```
                    ┌─────────────────────────────────┐
                    │            User                 │
                    └─────────────────────────────────┘
                         │              ▲
                         ▼              │
              ┌──────────────────┐      │
              │     Operate      │──────┘
              │                  │
              └──────────────────┘
                    ▲    │
                    │    ▼
    ┌───────────────────────────────────────────────────┐
    │                Technical System                    │
    │  ┌─────────┐   ┌─────────┐   ┌──────────┐        │
    │  │ Detect  │──▶│ Process │──▶│ Activate │        │
    │  │         │   │(Control)│   │          │        │
    │  └─────────┘   └────┬────┘   └──────────┘        │
    │       ▲             │              │              │
    │       │             ▼              │              │
    │       │       ┌─────────┐          │              │
    │       │       │Indicate │          │              │
    │       │       │         │          │              │
    │       │       └─────────┘          │              │
    │       │             │              │              │
    │       └─────────────┴──────────────┘              │
    └───────────────────────────────────────────────────┘
```

### Function Descriptions

| Function | Description | Defense System Examples |
|:---------|:------------|:------------------------|
| **Detect** | Sensors that convert physical quantities to signals | Camera (RCWS), Accelerometer (LOMAH), Trigger sensor (Simulator) |
| **Process (Control)** | Signal processing, computation, decision making | Fire control computer, AI processor, Ballistics calculator |
| **Activate** | Actuators that convert signals to physical action | Servo motors, Haptic feedback, Recoil simulation |
| **Indicate** | Displays that present information to user | HUD, Score display, Status indicators |
| **Operate** | User input and control interface | Joystick, Trigger, Console buttons |

### Application Rule

**When to apply Figure 6.11 pattern:**
- System involves sensors and actuators
- Closed-loop control is present
- Human-machine interface exists
- Microprocessor/microcontroller is central component

**All 15 defense training systems except Training Grenade benefit from this pattern.**
