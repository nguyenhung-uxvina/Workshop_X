## 1. Executive Summary

### Core Concept
Section 6.3.2 teaches the systematic methodology for decomposing complex overall functions into manageable subfunctions. This is a **foundational skill** in conceptual design that directly enables solution discovery by making complex problems tractable through hierarchical decomposition.

### Key Principles Extracted

| Principle | Definition | Strategic Importance |
|:----------|:-----------|:---------------------|
| **Complexity Reduction** | Break complex functions into simpler subfunctions | Enables parallel solution search |
| **Flow-Based Decomposition** | Start with main flow (E/M/S), add auxiliary flows later | Ensures systematic coverage |
| **Solution-Determining Functions** | Identify subfunctions that drive design decisions | Focus resources on critical paths |
| **Abstraction Level Control** | Match decomposition depth to problem novelty | Avoid over-engineering or under-specification |
| **Task-Specific vs General Functions** | Use generally valid functions to enable catalogues | Access proven solutions |

### Defense Application Relevance
Function decomposition is **critical** for Vietnamese defense systems because:
- Complex training systems require systematic breakdown
- Integration of indigenous and imported subsystems demands clear functional interfaces
- Military doctrine compliance (MIL-STD) requires traceable function-to-requirement mapping
- Limited R&D resources necessitate efficient solution search strategies

## 2. Skill 1: Feynman Technique Explanation

### 🎓 60-Second Explanation

**What it is:** Function decomposition is like disassembling a complex machine to understand each part's job. Instead of trying to solve "Make weapons training realistic" all at once, you break it into smaller jobs: "Simulate recoil," "Track hit accuracy," "Display results."

**Why it matters:** Your brain can only hold 5-9 things at once (Miller's Law). A 20-part problem overwhelms you. Five 4-part problems are manageable. Decomposition makes the impossible possible.

### 🏠 Everyday Analogy

**Making Phở (Vietnamese noodle soup):**

Overall function: "Produce delicious phở" → Too complex!

Decompose into subfunctions:
1. **Prepare broth** → simmer bones, add spices, clarify
2. **Prepare noodles** → soak, portion, blanch
3. **Prepare toppings** → slice meat, wash herbs, arrange garnishes
4. **Assemble** → combine elements, add condiments

Each subfunction can be solved independently, then integrated. A restaurant might have specialists for each subfunction, or one chef mastering each separately.

### 🎯 Defense System Example: LOMAH System

**Overall Function:** "Evaluate marksmanship training effectiveness"

**Decomposition Level 1 (Main Functions):**
```
                    ┌─────────────────┐
    S (Commands) ─→│  Evaluate       │─→ S (Performance Data)
    E (Power)    ─→│  Marksmanship   │─→ E (Heat loss)
    M (Ammo)     ─→│  Training       │─→ M (Spent casings)
                    └─────────────────┘
```

**Decomposition Level 2 (Subfunctions):**
```
                ┌────────────┐    ┌────────────┐    ┌────────────┐
    Signal  ─→  │  Detect    │ ─→ │  Process   │ ─→ │  Display   │ ─→ Signal
    (Shot)      │  Shot      │    │  Impact    │    │  Results   │    (Feedback)
                └────────────┘    └────────────┘    └────────────┘
                      │                │                │
                ┌─────┴─────┐    ┌─────┴─────┐    ┌─────┴─────┐
                │ Acoustic  │    │ Calculate │    │ Generate  │
                │ sensor    │    │ location  │    │ report    │
                └───────────┘    └───────────┘    └───────────┘
```

**Solution-Determining Subfunction:** "Detect Shot" is critical because:
- Sensor technology choice (acoustic, optical, electromagnetic) determines all downstream processing
- Detection accuracy limits overall system accuracy
- Environmental robustness (rain, wind, dust) depends on this subfunction

### ❓ Understanding Check

**Question:** Given a Target UAV system, which subfunction is likely solution-determining: "Generate thrust," "Simulate radar signature," or "Store telemetry"?

**Answer:** "Simulate radar signature" - This subfunction determines whether the target is tactically realistic. Without proper signature simulation, the entire system fails its training purpose regardless of how well it flies or stores data.

### ⚠️ Common Misconceptions

| Misconception | Reality |
|:--------------|:--------|
| "Main function = most important" | ALL subfunctions are necessary; "main" just means primary flow |
| "More decomposition = better" | Over-decomposition wastes time; match depth to novelty |
| "Subfunctions must be sequential" | Many subfunctions are parallel (energy conversion + signal processing) |
| "Start with solutions in mind" | Subfunctions must be solution-neutral; solutions come AFTER structure |

### Chunk 1: Complexity and Decomposition Logic
**Duration:** 45 minutes | **Difficulty:** ⭐⭐

#### Core Concepts (5-9 items)
1. Definition of complexity (transparency, process intricacy, component count)
2. Relationship between system ↔ subsystem ↔ element and function ↔ subfunction
3. Aims of decomposition: facilitate solution search + create unambiguous structure
4. Black-box thinking: inputs → function → outputs
5. The fuel gauge example as decomposition template
6. System boundary consideration: what's inside vs outside

#### Explanation

Complexity in engineering design has three dimensions. First, **transparency** refers to how clearly you can see the relationship between inputs and outputs. A hammer has high transparency (swing → impact); a smartphone has low transparency (touch → computation → display). Second, **process intricacy** describes how many physical phenomena interact. A lever uses one principle (mechanical advantage); a jet engine uses thermodynamics, fluid mechanics, combustion chemistry, and materials science simultaneously. Third, **component count** is simply how many parts are involved.

Function decomposition addresses all three dimensions by isolating subfunctions that have higher transparency, simpler processes, and fewer components than the overall function. The key insight is that **you don't need to understand everything at once**. By focusing on one subfunction at a time, you can apply your full cognitive capacity to each piece.

The fuel gauge example illustrates the process perfectly. "Measure and indicate quantities of liquid" is complex. But "receive signal" from a float, "channel signal" through wires, and "indicate signal" on a display are each simpler problems with known solutions.

#### Defense Application: 12.7mm RCWS

**Overall function:** "Provide remotely controlled suppressive fire"

**Complexity assessment:**
- Transparency: LOW (operator input → engagement is not obvious)
- Process intricacy: HIGH (ballistics, servo control, sensor fusion, communication)
- Component count: HIGH (weapon, mount, sensors, actuators, computers, displays)

**Decomposition rationale:**
Breaking into "Acquire target," "Aim weapon," "Fire weapon," "Stabilize platform" creates subfunctions where each has higher transparency and simpler processes.

#### Practice Exercise

**Task:** Given the Target USV system with overall function "Simulate hostile naval threat," identify why this is complex using the three dimensions.

**Expected answer:**
- Transparency: LOW (control inputs → realistic threat behavior requires AI interpretation)
- Process intricacy: HIGH (hydrodynamics, propulsion, communication, navigation, signature enhancement)
- Component count: HIGH (hull, propulsion, sensors, communication, payload, power systems)

#### Self-Check Questions
- Can you explain the three dimensions of complexity?
- Can you articulate why decomposition helps with each dimension?
- Can you identify system boundaries for a given function?

### Chunk 2: Main Flow vs Auxiliary Flow Strategy
**Duration:** 60 minutes | **Difficulty:** ⭐⭐⭐

#### Core Concepts
1. Main flow: the primary E/M/S transformation defining system purpose
2. Auxiliary flows: supporting E/M/S transformations enabling main flow
3. Sequential decomposition: main flow first, auxiliary flows second
4. Working structure concept: temporary solution to guide auxiliary flow identification
5. Flow coupling: how auxiliary flows connect to main flow subfunctions
6. The potato harvester example: material main flow with energy auxiliary
7. System boundary decisions based on existing solutions availability

#### Explanation

Every technical system has a **main flow** that represents its core purpose. For a training grenade, the main flow is material (grenade body trajectory). For the RAMS system, the main flow is signal (marksmanship data). For a UAV catapult, the main flow is energy (kinetic energy to launch vehicle).

**Auxiliary flows** support the main flow but are not the primary purpose. The training grenade needs energy (propellant) and signals (fuze timing). The RAMS needs energy (power) and material (sensors, displays). The UAV catapult needs signals (launch commands) and material (catapult structure).

The strategic principle is: **Start with main flow decomposition, then add auxiliary flows.** This prevents getting lost in secondary details before understanding the core transformation.

The text recommends creating a **temporary working structure** or provisional solution after the basic main flow structure is established. This isn't the final solution - it's a thinking tool that reveals what auxiliary subfunctions are needed. For example, sketching a pneumatic catapult helps you realize you need "supply compressed air" and "control release timing" as auxiliary subfunctions.

#### Defense Application: Tethered Drone System

**Main Flow:** Energy (power to keep drone aloft and operational)
```
E_input (ground power) → [Tethered Drone] → E_output (flight energy + sensor power)
```

**Main Flow Decomposition:**
1. Convert ground power to transmission format
2. Transmit power through tether
3. Convert to drone operating voltages
4. Distribute to flight systems and payload

**Auxiliary Flows:**
- **Material:** Tether management (deploy, retrieve, tension control)
- **Signal:** Flight commands, sensor data, status telemetry

**Working Structure Insight:** Sketching a preliminary solution (fiber-optic tether with copper conductors) reveals auxiliary subfunctions like "separate optical from electrical paths" and "manage tether spool dynamics."

#### Practice Exercise

**Task:** For the Naval Weapon Simulator, identify the main flow and three auxiliary flows with at least one subfunction each.

**Expected Answer:**
- **Main flow:** Signal (training scenario → tactical decisions → simulated engagement outcomes)
  - Subfunctions: Generate scenario, Process decisions, Calculate outcomes, Display results
- **Auxiliary flow 1:** Energy (power system simulation)
  - Subfunctions: Simulate power states, Model power failures
- **Auxiliary flow 2:** Material (simulated ammunition handling)
  - Subfunctions: Track virtual magazine, Simulate reload sequences
- **Auxiliary flow 3:** Signal (instructor controls)
  - Subfunctions: Inject faults, Modify scenario parameters

### Chunk 3: Decomposition Depth Strategies
**Duration:** 60 minutes | **Difficulty:** ⭐⭐⭐⭐

#### Core Concepts
1. Optimum decomposition depth: balance novelty and search method
2. Original design vs adaptive design decomposition strategies
3. Modular systems: physical structure must reflect function structure
4. Stopping criteria: when is decomposition sufficient?
5. Generally valid functions vs task-specific functions
6. Classification scheme utility for decomposition
7. Analysis of existing systems for adaptive design

#### Explanation

The text poses a crucial question: **How deep should you decompose?** Too shallow and the subfunctions remain too complex to solve. Too deep and you waste effort specifying obvious details.

Three factors determine optimal depth:

**1. Problem Novelty:**
- **Original design** (no prior solution exists): Decompose deeply until subfunctions match known working principles
- **Adaptive design** (modifying existing solution): Analyze existing product to get function structure, modify only what requirements demand
- **Variant design** (parameter changes only): Minimal decomposition, focus on changed parameters

**2. Search Method:**
- If using design catalogues → decompose to generally valid functions (they match catalogue entries)
- If using brainstorming → can use task-specific functions (creativity fills gaps)
- If using morphological matrix → need comparable abstraction levels across alternatives

**3. Team Capability:**
- Experienced team with domain knowledge → shallower decomposition (implicit knowledge fills gaps)
- New team or novel domain → deeper decomposition (explicit structure prevents oversights)

**Generally Valid Functions** (Table 6.1 in original) provide decomposition templates:
- Energy: Change, Vary, Connect (with signal), Channel, Store
- Material: Change, Vary, Connect (with E/S), Channel, Store, Separate
- Signal: Change, Vary, Amplify, Connect, Channel, Store

These functions recur across domains and enable access to design catalogues.

#### Defense Application: AR-VR Weapon Simulator

**Novelty Assessment:** Adaptive design (VR technology exists, military training context is specific)

**Decomposition Strategy:**
1. Analyze existing commercial VR systems for baseline function structure
2. Identify military-specific modifications (weapon handling realism, MIL-STD compliance)
3. Decompose only novel subfunctions deeply (e.g., "simulate recoil" is novel for VR)

**Function Structure with Mixed Depth:**
```
┌─────────────────────────────────────────────────────────────────┐
│                    AR-VR Weapon Simulator                       │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  ┌──────────────┐    ┌──────────────┐    ┌──────────────┐      │
│  │ Generate     │ ─→ │ Render       │ ─→ │ Display      │      │
│  │ scenario     │    │ graphics     │    │ output       │      │
│  └──────────────┘    └──────────────┘    └──────────────┘      │
│       ↓ (adaptive)        ↓ (catalog)       ↓ (catalog)        │
│    [Use existing      [Standard VR       [Commercial          │
│     scenarios]         pipeline]          HMD]                 │
│                                                                 │
│  ┌──────────────┐    ┌──────────────┐    ┌──────────────┐      │
│  │ Track        │ ─→ │ Process      │ ─→ │ Simulate     │      │
│  │ user motion  │    │ interaction  │    │ weapon       │      │
│  └──────────────┘    └──────────────┘    │ feedback     │      │
│       ↓ (catalog)        ↓ (original)   └──────────────┘      │
│    [Commercial         [NOVEL: weapon       ↓ (ORIGINAL)       │
│     tracking]           handling logic]  [Deep decomposition]  │
│                                                                 │
│                    ┌───────────────────────────────────────┐   │
│                    │ Simulate Weapon Feedback (NOVEL)      │   │
│                    ├───────────────────────────────────────┤   │
│                    │ - Generate recoil force               │   │
│                    │ - Simulate weapon weight              │   │
│                    │ - Provide trigger resistance          │   │
│                    │ - Create muzzle blast effect          │   │
│                    │ - Simulate magazine changes           │   │
│                    └───────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────────────┘
```

#### Stopping Criteria Checklist

Stop decomposing when:
- [ ] Each subfunction has at least one known working principle
- [ ] Complexity is low enough for single-engineer ownership
- [ ] Interfaces between subfunctions are clear
- [ ] Existing assemblies can be assigned to subfunctions
- [ ] Catalogue lookup is possible for generally valid functions

Continue decomposing when:
- [ ] No working principle is known for a subfunction
- [ ] Subfunction still spans multiple disciplines
- [ ] Interfaces remain ambiguous
- [ ] Novel physical effects are involved

#### Comprehensive Exercise: UAV Catapult System

**Step 1: Overall Function**
```
                    ┌─────────────────────┐
    E (stored)  ─→  │    Launch UAV       │  ─→  E (kinetic)
    M (UAV)     ─→  │    to flight speed  │  ─→  M (UAV airborne)
    S (command) ─→  │                     │  ─→  S (status)
                    └─────────────────────┘
```

**Step 2: Identify Main Flow**
- Main flow: **Energy** (converting stored energy to UAV kinetic energy)
- Rationale: The system's core purpose is energy transformation; the UAV (material) is unchanged, commands (signal) are enablers

**Step 3: Decompose Main Flow**
```
┌────────────┐    ┌────────────┐    ┌────────────┐    ┌────────────┐
│  Store     │ ─→ │  Release   │ ─→ │  Transfer  │ ─→ │  Accelerate│
│  energy    │    │  energy    │    │  to UAV    │    │  UAV       │
└────────────┘    └────────────┘    └────────────┘    └────────────┘
    (pneumatic,       (valve,          (rail,           (sustained
     bungee, etc)      latch)           carriage)        force)
```

**Step 4: Identify Solution-Determining Subfunction**
- "Store energy" is solution-determining because:
  - Energy storage mechanism (pneumatic, bungee, electromagnetic) determines all other subfunctions
  - Field deployment constraints (portability, refueling) depend on storage choice
  - Cost and reliability vary dramatically by storage method

**Step 5: Add Auxiliary Flows**
```
Signal Auxiliary:
┌────────────┐    ┌────────────┐    ┌────────────┐
│  Receive   │ ─→ │  Verify    │ ─→ │  Trigger   │
│  command   │    │  ready     │    │  release   │
└────────────┘    └────────────┘    └────────────┘

Material Auxiliary:
┌────────────┐    ┌────────────┐    ┌────────────┐
│  Position  │ ─→ │  Secure    │ ─→ │  Release   │
│  UAV       │    │  UAV       │    │  UAV       │
└────────────┘    └────────────┘    └────────────┘
```

**Step 6: Vietnamese Context Adaptation**
- Energy storage: Prefer pneumatic or bungee (available locally) over electromagnetic (import-dependent)
- Signal processing: Use indigenous control electronics where possible
- Material handling: Design for field maintenance with basic tools
- Environmental: 85% humidity, 45°C temperatures, salt air if coastal

## 4. Skill 3: Design Review Criteria

### Function Decomposition Quality Checklist

#### Phase Gate: Conceptual Design Entry

| Criterion | Weight | Evaluation Questions |
|:----------|:------:|:---------------------|
| **Completeness** | 20% | Does the structure account for all required inputs/outputs? Are auxiliary flows identified? |
| **Appropriate Depth** | 20% | Is decomposition deep enough for solution search? Not over-decomposed? |
| **Solution Neutrality** | 15% | Are subfunctions expressed as transformations, not mechanisms? |
| **Interface Clarity** | 15% | Are connections between subfunctions explicit (E/M/S type, direction)? |
| **Flow Consistency** | 10% | Is E/M/S conserved? What enters must exit or be transformed. |
| **Hierarchy Logic** | 10% | Does each level represent meaningful complexity reduction? |
| **Solution-Determining ID** | 10% | Is the critical subfunction identified and prioritized? |

#### Scoring Rubric

**5 - Excellent:**
- All flows accounted for with clear interfaces
- Decomposition depth matches problem novelty
- Solution-neutral language throughout
- Solution-determining subfunction explicitly identified
- Ready for working principle search

**4 - Good:**
- Minor gaps in auxiliary flows
- Decomposition slightly too deep or shallow
- One or two subfunctions hint at solutions
- Interfaces mostly clear
- Needs minor revision before solution search

**3 - Acceptable:**
- Main flow decomposed correctly
- Auxiliary flows incomplete
- Some solution bias in subfunction naming
- Interfaces need clarification
- Requires significant revision

**2 - Needs Work:**
- Decomposition incomplete
- Significant solution bias
- Unclear interfaces
- Missing auxiliary flows
- Return to basics

**1 - Inadequate:**
- Fundamental misunderstanding of decomposition
- Not solution-neutral
- Major structural errors
- Extensive rework required

### Common Review Findings (Vietnamese Defense Context)

| Finding | Frequency | Root Cause | Remediation |
|:--------|:---------:|:-----------|:------------|
| Premature solution commitment | 40% | Jumping to known solutions | Return to black-box thinking |
| Shallow decomposition | 25% | Over-confidence in tacit knowledge | Apply stopping criteria |
| Missing auxiliary flows | 20% | Focus only on main transformation | Systematic E/M/S check |
| Unclear system boundary | 10% | Scope creep or ambiguous requirements | Revisit Task Clarification |

**Weakness Addressed:** Cannot correctly identify which flow (E/M/S) is primary
**Difficulty:** ⭐⭐ | **Duration:** 25 minutes

#### Problem 1: Training Grenade System
**Scenario:** System must simulate realistic grenade effects during training exercises.

**Task:** Identify the main flow and justify your choice.

**Your Answer Space:**
```
Main Flow: _____________ (Energy / Material / Signal)

Justification:
_____________________________________________
_____________________________________________
```

**Model Answer:**
Main Flow: **Material** (the grenade body is the primary object being transformed - from static to projected to effect-producing)

Justification: The core purpose is transforming the grenade's state (from ready → thrown → detonated → effect displayed). Energy (propulsion) and Signal (timing) are auxiliary - they enable the material transformation but aren't the primary output the system produces.

_____________________________________________
_____________________________________________

The physical platform (material) and power source (energy) are auxiliary - they enable signal generation but aren't the primary transformation.

### Drill Set 2: Decomposition Depth Selection
**Weakness Addressed:** Decomposes too shallow or too deep
**Difficulty:** ⭐⭐⭐ | **Duration:** 30 minutes

#### Problem 1: Depth Decision
**Scenario:** You are designing an **original** Small Arms Simulator. You have reached this subfunction:

```
┌─────────────────────────────────────┐
│      Track weapon orientation       │
│      (position and direction)       │
└─────────────────────────────────────┘
```

**Task:** Should you decompose further? If yes, propose subfunctions. If no, justify stopping.

**Your Answer Space:**
```
Decision: □ Decompose Further    □ Stop Here

If decompose - Subfunctions:
1. _______________________________
2. _______________________________
3. _______________________________

If stop - Justification:
_____________________________________________
```

**Model Answer:**
Decision: **Decompose Further** (for original design)

Subfunctions:
1. Detect weapon position (where is it?)
2. Detect weapon direction (where is it pointing?)
3. Convert detection to coordinate signal
4. Reference to world/target coordinate system

Reasoning: For original design, we need to reach subfunctions where working principles can be searched. "Track weapon orientation" is still too complex - multiple technologies could do this (optical, magnetic, inertial, IR), but we need to understand WHAT specifically must be detected before searching HOW. The subfunctions above clarify that position AND direction must both be detected and converted to usable coordinates.

Solution-determining subfunction: **Stabilize platform**

1. **Function decomposition is foundational** - It determines the solution space breadth and enables systematic search

2. **Match depth to novelty** - Original designs need deep decomposition; adaptive designs use existing structures

3. **Main flow first, auxiliary flows second** - Prevents getting lost in secondary details

4. **Solution-determining subfunctions deserve priority** - Focus resources on critical path

5. **Generally valid functions enable catalogues** - Access proven solutions through standard terminology

6. **Vietnamese context matters** - Add environmental protection, indigenous manufacturing, and local supply chain considerations as explicit subfunctions
